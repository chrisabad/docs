AgentOS runs on a single **cloud VPS** (Debian, reached over Tailscale only). The entire control plane is one Docker container with an **embedded** PostgreSQL — there is no separate database container. A Traefik container provides TLS and public routing.

<Note>
AgentOS migrated from a macOS host (node name **Lauryn**) to this VPS. Earlier docs describing macOS `launchd` services, a self-hosted LiteLLM proxy, or a Neo4j/Graphiti "intelligence pipeline" are obsolete — none of those run here. Models are called **directly against Ollama Cloud** (`https://ollama.com/v1`) via each agent's `OLLAMA_API_KEY`.
</Note>

## Embedded PostgreSQL

Paperclip uses the `@embedded-postgres` npm package — Postgres runs **inside** the Paperclip container, started by the app, not as its own service.

| Property | Value |
|----------|-------|
| Data dir | `/paperclip/instances/default/db` |
| Port | `54329` (listens on the Unix socket in `/tmp`, **not** exposed to the host) |
| User / password / database | `paperclip` / `paperclip` / `paperclip` |
| Encoding | UTF8 |
| `psql` client | `/usr/bin/psql` (Postgres 17 client, inside the container) |

Because the port is not published to the host, connect **from inside the container**:

```bash
docker exec -e PGPASSWORD=paperclip paperclip-ezk7-paperclip-1 \
  psql -h /tmp -p 54329 -U paperclip -d paperclip -c "SELECT count(*) FROM issues;"
```

<Warning>
The DB is the fleet's source of truth. There is no separate DB container to fail over to. The entrypoint runs a WAL-corruption pre-flight check and auto-applies `pg_resetwal` if it detects corruption on startup (`/docker/paperclip-ezk7/patches/docker-entrypoint.sh`).
</Warning>

## Patches mechanism

Paperclip is the upstream `paperclipai` npm package with **targeted patches applied at container entrypoint** (not build time). This keeps upstream sync easy while layering in fleet-specific fixes (recovery caps, execution-policy fallback, phantom-blocked guards, etc.).

| Property | Value |
|----------|-------|
| Live patches dir | `/docker/paperclip-ezk7/patches/*.patch` |
| Applied by | `/docker/paperclip-ezk7/patches/apply-patches-docker.sh` (runs at entrypoint) |
| Target root | `/usr/local/lib/node_modules/paperclipai/node_modules/` |
| **Source of truth (version-controlled)** | `agentos-config/paperclip-patches/` |

Patches use a custom **MATCH/REPLACE** format (not unified diff). Each file has a `--- Target:` header naming the file to patch, then a `MATCH:` block and a `REPLACE:` block. Application is idempotent — `apply-patches-docker.sh` skips a patch whose REPLACE text is already present and fails loudly if the MATCH text is missing (i.e. the patch is stale against the current Paperclip version).

```bash
# Dry-run: report which patches are applied / needed / stale
docker exec paperclip-ezk7-paperclip-1 /docker/paperclip-ezk7/patches/apply-patches-docker.sh --check
```

**To add a durable server patch:** add the `.patch` file to `agentos-config/paperclip-patches/` via PR, deploy it to `/docker/paperclip-ezk7/patches/`, and it will be applied (and re-applied on every restart) automatically. See `058-plugin-worker-board-key-env.patch` for a minimal template.

## Plugins

The issue-trigger plugin (routing, lifecycle, sweeps) is deployed at:

- **Deployed dist:** `/docker/paperclip-ezk7/data/plugins/kaleidoscope-issue-trigger/`
- **Source repo:** `paperclip-issue-trigger` (`agentos-config` sibling; built with esbuild)

Bumping the plugin's `paperclip.manifest.json` version triggers a worker reload.
