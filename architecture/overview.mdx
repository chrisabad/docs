AgentOS is a cloud-hosted multi-agent platform running on a single VPS (Debian 13, kernel 6.8.0-117). It orchestrates AI agents across seven companies through a layered architecture where every component has a well-defined role: inbound routing, session dispatch, model selection, work management, and health monitoring.

<Note>
AgentOS migrated from macOS (node name: Lauryn) to a cloud VPS in 2026. The old dual-gateway launchd architecture has been replaced by a single Hermes gateway running inside a Docker container with s6-overlay supervision.
</Note>

## Layers

### 1. Inbound layer

External services send events via webhooks or are polled by intelligence connectors.

| Component | What it does |
|-----------|-------------|
| **Slack** | DMs to Juno arrive via HTTP webhook. Slack is the only human-facing channel. |
| **Gmail connectors** | `gmail-dispatcher` and `gmail-multiwatch` ingest email events. |
| **Intelligence connectors** | Calendar, email, Granola, and Slack connectors feed the memory/Graphiti layer. |
| **Webhook proxies** | Smart, Figma, and Frame.io proxies route inbound hooks to the gateway. |

<Note>
The Memory Service (port 8010) and Notification Service (port 8012) are part of the Intelligence & Memory layer. On the cloud VPS, these services are **not running** — agents operating on VPS must skip I&M layer calls and use Paperclip issue comments for coordination instead.
</Note>

### 2. Gateway layer

A single Hermes gateway process handles all agent orchestration, running inside a Docker container with s6-overlay supervision.

| Component | Port | Purpose |
|-----------|------|---------|
| Hermes Gateway | host network | Agent dispatch, ACP routing, session management |
| Hermes Dashboard | 9119 (localhost only) | API key management, run history |
| Paperclip | 3100 | Issue tracker, agent dispatch, plugins |
| Paperclip PostgreSQL | 54329 | Database backend |

<Note>
The previous architecture used two separate launchd-managed Node.js gateways (Gateway-1 on port 18790 for AGE, Gateway-2 on port 18793 for business companies). On the cloud VPS, both are replaced by the single Hermes gateway using `provider: auto` model routing.
</Note>

### 3. Agent runtime

The gateway hosts an **ACP (Agent Communication Protocol)** dispatch system with three priority lanes:

- **Interactive** — Slack DMs to Juno, highest priority, never queued behind batch work
- **Heartbeat** — Cron/scheduled runs, medium priority
- **Main** — Paperclip issue execution, normal priority

Each agent runs via the `hermes_local` adapter inside the Docker container. Agent profiles live at `/opt/hermes-profiles/<name>/config.yaml`. The `provider: auto` setting routes model calls through the Hermes gateway to the cheapest available provider.

### 4. Model routing (LiteLLM)

All model calls go through a LiteLLM proxy (Docker container, port 4000) that maps **semantic model names** to provider chains with automatic fallback. Agents never call model providers directly. See [Model Routing](/architecture/model-routing) for the full routing table.

### 5. Work management (Paperclip)

Paperclip is the issue tracker that drives all agent work:

- Seven companies with isolated issue boards
- **Issue Trigger Plugin** handles lifecycle transitions including review gates and approval flows
- Agents pick up assigned issues, execute, submit for review, and close
- The Paperclip API is at `https://paperclip-ezk7.srv1710374.hstgr.cloud/api`

<Note>
Reed (the cross-company dispatcher agent) is no longer in the AGE fleet. Issue dispatching is now handled by the Paperclip issue-trigger plugin and wake-on-demand assignment.
</Note>

### 6. Health and recovery

A unified health daemon monitors subsystems and auto-heals failures. The s6-overlay supervision tree inside the Hermes container manages gateway process lifecycle, automatic restarts, and log rotation. See [Health System](/operations/health-system) for details.

## Key design decisions

<AccordionGroup>
  <Accordion title="Why a single Hermes gateway?">
    The original dual-gateway design (separate AGE and business gateways) added complexity without proportional reliability benefit. The Hermes gateway consolidates routing into a single process with s6-overlay supervision for automatic restart. Model routing through `provider: auto` eliminates the need for separate gateway configurations.
  </Accordion>
  <Accordion title="Why Paperclip over Linear for agent work?">
    Linear is used for human project management (contractor tracking at Weekend). Paperclip is purpose-built for agent issue lifecycle: native heartbeats, wake-on-demand, execution locking, and custom plugins. Agents don't need kanban boards — they need queue dispatch.
  </Accordion>
  <Accordion title="Why patches instead of a fork?">
    The OpenClaw gateway is open source. Rather than maintaining a full fork, AgentOS applies approximately 78 targeted patches on top of the upstream `main` branch. The patch system (`/patches/apply-patches-docker.sh`) applies these during container build. This keeps upstream sync easy while adding features like priority lanes, task panels, and circuit breakers.
  </Accordion>
  <Accordion title="Why Ollama Cloud as primary model provider?">
    Cost sensitivity. Ollama Cloud provides GLM 5.1 and Qwen3-Coder at lower cost than frontier APIs. Claude (via OAuth) and Gemini are fallbacks for when Ollama is unavailable or too slow.
  </Accordion>
  <Accordion title="Why isn't the dashboard exposed on the network?">
    The Hermes dashboard at port 9119 stores API keys and agent tokens. Exposing it without authentication is unsafe. Access it via SSH tunnel: `ssh -L 9119:localhost:9119 user@vps-host`. Never configure it with `--host 0.0.0.0` unless behind an authenticated reverse proxy.
  </Accordion>
</AccordionGroup>
