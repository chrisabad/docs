title: "AgentOS System Architecture: How It All Fits Together"
description: "A top-down walkthrough of AgentOS on a single VPS: Paperclip as the control plane, Hermes agents spawned per-run inside the container, and models called directly against Ollama Cloud."
---

AgentOS is a cloud-hosted multi-agent platform running on a single VPS (Debian, reached over Tailscale only). It orchestrates AI agents across seven companies. The control plane is **one Docker container** (Paperclip), agents are **Hermes processes spawned per run**, and model calls go **directly to Ollama Cloud**.

<Note>
AgentOS migrated from a macOS host (node name **Lauryn**) to this VPS. The old architecture — dual `launchd` gateways, a self-hosted LiteLLM proxy, and a Neo4j/Graphiti intelligence pipeline — is **gone**. Docs describing those are obsolete. There is no persistent "Hermes gateway" service and no separate database, LiteLLM, or dashboard container.
</Note>

## Layers

### 1. Inbound

| Channel | What it does |
|---------|-------------|
| **Slack DM → Juno** | The only human-facing channel. Chris DMs Juno; no other agent talks to Slack directly. |
| **Paperclip API** | `https://paperclip-ezk7.srv1710374.hstgr.cloud/api` — issue creation, comments, assignment drive all agent work. |

<Note>
The legacy Intelligence & Memory services (Memory `:8010`, Notification `:8012`) and the Graphiti/Neo4j pipeline are **not running** on this VPS. Agents coordinate through Paperclip issue comments, not an I&M layer.
</Note>

### 2. Control plane — Paperclip (one container)

Everything runs inside `paperclip-ezk7-paperclip-1`:

| Piece | Detail |
|-------|--------|
| Paperclip server | upstream `paperclipai` + entrypoint patches; serves port 3100 (Traefik-fronted) |
| Embedded PostgreSQL | inside the container, socket `/tmp` port `54329`, data `/paperclip/instances/default/db` — **no separate DB container** |
| Issue-trigger plugin | lifecycle automation: routing, review/approval gates, sweeps |
| `hermes_local` adapter | spawns agent runs (below) |

See [Docker & the Paperclip Container](/operations/docker) for the verified container/DB/patches reference.

### 3. Agent runtime — Hermes, spawned per run

There is **no persistent Hermes gateway process** and no separate Hermes container. When Paperclip dispatches work to an agent, its built-in **`hermes_local` adapter** execs that agent's wrapper as a subprocess **inside the Paperclip container**:

```
/opt/hermes-wrappers/<agent>.sh  →  /usr/local/bin/hermes  (the mounted venv)
```

The host's Hermes runtime is **bind-mounted** into the container (from `docker-compose.yml`):

- `/opt/hermes-venv` → the `hermes` binary (read-only)
- `/opt/hermes-profiles/<agent>/` → per-agent `SOUL.md`, `AGENTS.md`, `HEARTBEAT.md`, `TOOLS.md`, `config.yaml`, skills (read-write)
- `/opt/hermes-wrappers/<agent>.sh` → per-agent launch wrapper (read-only)
- `/opt/hermes-workspace` → shared workspace

Agents wake on Paperclip events (issue assigned, comment mention, approval resolved) or scheduled crons. The run is a fresh `hermes` process that exits when the turn completes — state persists in the agent's `state.db` and in Paperclip.

### 4. Model routing — direct to Ollama Cloud

There is **no LiteLLM proxy**. Each agent's `config.yaml` points `provider: auto` at Ollama Cloud directly:

```yaml
model:
  default: glm-5.1:cloud
  provider: auto
  base_url: https://ollama.com/v1
  api_key: ${OLLAMA_API_KEY}
```

Current model assignments (under active evaluation):

| Agent | Model |
|-------|-------|
| Juno, Quinn, Ellis | `glm-5.1` |
| Axel, Vera, Dex, Orion | `gpt-oss:20b` |

<Note>
The split is being evaluated. `gpt-oss:20b` has exhibited a false-`401` failure mode where the model validates its API key by echoing it, sees Hermes's masked `***`, and aborts (tracked in AGE-325). Prefer `glm-5.1` for agents doing API-heavy work until resolved.
</Note>

### 5. Work management — Paperclip

- Seven companies with isolated issue boards (AGE, WEE, FON, KAL, DIA, PIX, STU).
- The **issue-trigger plugin** drives lifecycle: `workMode=planning` on new top-level issues, execution-policy review/approval gates, and recovery sweeps.
- Execution policy (review → approval) is applied **at issue creation** via the company/project `default_execution_policy` fallback; `workMode=planning` is set per-issue by the plugin (child tasks excluded).
- Agents pick up assigned issues, execute, submit to `in_review`, and a reviewer/approver closes them.

### 6. Health and recovery

Paperclip's own recovery logic (stranded-issue detection, run-failure handling, recovery-cascade guards) plus the issue-trigger plugin's sweeps handle most self-healing. The container entrypoint runs a PostgreSQL WAL pre-flight check and auto-applies `pg_resetwal` on detected corruption.

## Key design decisions

<AccordionGroup>
  <Accordion title="Why one container with embedded Postgres?">
    The whole control plane — server, DB, plugin host, and agent dispatch — ships as a single Hostinger image (`ghcr.io/hostinger/hvps-paperclip`). Embedded Postgres removes a moving part; the trade-off is no DB failover, mitigated by the WAL pre-flight check at entrypoint.
  </Accordion>
  <Accordion title="Why Hermes per-run instead of a persistent gateway?">
    The old dual-gateway (launchd) design ran always-on processes per company. The `hermes_local` adapter instead spawns a fresh `hermes` process per run and tears it down at completion — simpler lifecycle, no gateway to supervise, state lives in Paperclip + each agent's `state.db`.
  </Accordion>
  <Accordion title="Why Ollama Cloud directly (no LiteLLM)?">
    Cost, and one fewer service to run. Ollama Cloud serves GLM-5.1, gpt-oss, and qwen3-coder cheaply; `provider: auto` handles selection. The self-hosted LiteLLM proxy from the macOS era was removed in the migration.
  </Accordion>
  <Accordion title="Why patches instead of forking Paperclip?">
    Rather than fork `paperclipai`, AgentOS applies targeted MATCH/REPLACE patches at container **entrypoint** (`/docker/paperclip-ezk7/patches/apply-patches-docker.sh`), source-controlled in `agentos-config/paperclip-patches/`. Easy upstream sync; fleet-specific behavior layered on top.
  </Accordion>
  <Accordion title="Why Paperclip over Linear for agent work?">
    Linear is for human project management. Paperclip is purpose-built for agent lifecycle: wake-on-demand, execution locking, review/approval gates, and custom plugins.
  </Accordion>
</AccordionGroup>
